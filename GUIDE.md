# Developer Guide

This guide covers how the `webapp` Flutter landing page is put together, how
to run and build it, and things a new contributor should know before making
changes. Everything here is based on reading the actual code in this repo.

## What this project is

`webapp` is a single-page Flutter Web app: one `HomePage` widget that shows a
nav bar and a hero section, and re-flows itself between a "large screen" and
"small screen" layout. There's no routing, no backend calls, and no state
management beyond plain `StatelessWidget`s. It reads as a hands-on exercise
for learning responsive layout in Flutter Web (the original README links to a
"Flutter Web: Responsive Landing Page" tutorial video), not a production
product — the brand name ("Advid Technologies"), hero copy ("Online Library
Management System"), and small-screen copy ("Mingalarbar!", "Say Hi to 🐱",
"LET'S FLY TO MARS") don't form a single coherent product story, and none of
the interactive elements (nav links, hamburger icon, "Notify" button) are
wired up to do anything.

## How the UI is structured

Entry point: `lib/main.dart`

- `main()` calls `runApp(MaterialApp(...))` with `home: HomePage()`.
- `HomePage` sets a solid dark-blue background (`0xFF2F2FA2`) and stacks
  `NavBar()` then `Body()` in a scrollable `Column`.
- `Body` delegates to `ResponsiveLayout` (`lib/utils/responsiveLayout.dart`),
  which picks between `LargeChild` and `SmallChild` based on the available
  width from `LayoutBuilder`.
  - `> 800px` → `LargeChild`
  - `<= 800px` (and, due to how the branches are written, also anything
    Flutter can't otherwise classify) → `SmallChild`
  - Note: `ResponsiveLayout` also defines a `mediumScreen` slot and
    `isMediumScreen`/`isLargeScreen` static helpers, but the widget's own
    `build()` method never actually reaches the medium branch — the `if
    (constraints.maxWidth > 800)` check is checked first, so the "medium"
    `else if` is dead code. If you extend this component, you'll likely want
    to fix that branch ordering.
- `LargeChild` renders `book.png` on the right and, on the left, "Online
  Library Management System" plus the `Search()` widget.
- `SmallChild` stacks a "Mingalarbar!" greeting, `cat-lady.png`, and another
  `Search()` widget.

Shared widgets, under `lib/widgets/`:

- `NavBar` — brand badge ("Advid Technologies") + text nav links (`Products`,
  `Solutions`, `Customers`, `Resources`, `Login`). On small screens (checked
  via `ResponsiveLayout.isSmallScreen`) it swaps the links for a static
  hamburger icon image. None of the links or the icon have tap handlers.
- `Search` — a white, rounded "pill" containing a `TextField` (hint: "Your
  Email Address") and a `SendBtn`.
- `SendBtn` — a gradient "Notify" button with a paper-plane icon. Its
  `onTap: () {}` is empty, so it currently does nothing when pressed. If you
  want to make the email capture functional, this is the file to wire up
  (e.g. to call a mailing-list API, at which point you'd add an HTTP client
  dependency and it would make sense to add an `API_REFERENCE.md`).

`lib/utils/responsiveLayout.dart` is the only utility/helper file — a
`StatelessWidget` plus three static breakpoint helpers keyed off
`MediaQuery.of(context).size.width`.

## Assets

Images live in `assets/` and are referenced with `Image.network("assets/...")`
rather than `Image.asset(...)`. This works for the deployed web build because
the assets are served as static files at that relative path, but note the
project's `pubspec.yaml` does **not** declare an `assets:` section — so these
images are not bundled the normal Flutter way and this app is effectively
web-only. Attempting to run it as a native iOS/Android build would not show
the images correctly. The `android/` and `ios/` folders here are just the
default `flutter create` platform scaffolding and are not the deployment
target.

freepik.com, icons from icons8.com.

## Running the project

```bash
flutter pub get
flutter run -d chrome
```

`flutter run` will hot-reload as you edit files under `lib/`.

## Building and deploying

The project ships as a static site via GitHub Pages, configured to serve from
`master` branch, `/docs` folder (see the "GitHub Pages Setting" section that
was in the original README).

To publish a new build:

```bash
flutter build web
```

Then copy the contents of `build/web/` into `docs/` (replacing the existing
files) and commit both. The `docs/` folder in this repo is a checked-in,
already-built snapshot of the app — it's what GitHub Pages actually serves,
and it is not automatically regenerated by any CI in this repo (there is no
CI configuration present).

## Tests

`test/widget_test.dart` is the default Flutter template test scaffolded by
`flutter create` — it calls `pumpWidget(HomePage())` but then asserts on
`find.text('0')` / a counter increment, which doesn't exist anywhere in this
app's actual UI. Running `flutter test` against this file will fail. If you
pick up this project, either delete this stale test or replace it with
assertions against real widgets (e.g. finding the "Notify" text or the email
`TextField`).

## Things to know before contributing

- No null-safety: the SDK constraint in `pubspec.yaml` (`>=2.7.0 <3.0.0`) predates
  Dart's sound null-safety, and the code uses the old-style nullable-by-default
  syntax (e.g. `Key key` instead of `Key? key` in `ResponsiveLayout`'s
  constructor). Migrating to a modern Flutter/Dart SDK will require running
  `dart migrate` or manually adding `?`/`required` annotations.
- No external services: there is no `http`, `dio`, or similar package in
  `pubspec.yaml`, and no network calls anywhere in `lib/`. If you add one
  (e.g. to make the "Notify" button actually submit an email), document it in
  a new `API_REFERENCE.md`.
- No state management library — everything is a `StatelessWidget`, so there is
  no app state to reason about beyond widget props.
- The screenshots in the repo root (`Screen Shot 2021-01-07 ....png`) are what
  the original author used in the README to show the fullscreen and
  responsive views; they still match the current UI.
